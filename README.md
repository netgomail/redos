# РедОС

> Консольная утилита для специалиста по защите информации — парольная и USB-политики, печать и сканирование, инвентаризация Linux-систем. Заточена под РедОС 7/8 (RHEL-based).

---

## Установка

```bash
curl -fsSL https://raw.githubusercontent.com/netgomail/redos/master/install.sh | bash
```

Установщик автоматически скачивает последнюю версию из GitHub Releases и добавляет `redos` в PATH.

## Обновление

```bash
redos update
```

| Команда | Описание |

| `/usb-policy` | Контроль устройств на правилах udev — блокировка групп USB-устройств на уровне ядра. |

### Оборудование

| Команда | Описание |
|---|---|

### Инвентаризация

| Команда | Описание |
|---|---|
| `/inventory [файл.txt]` | Инвентаризация системы: ОС, железо, диски, пользователи, сеть, открытые порты, сервисы. |

Все команды кроме `/inventory` требуют root — в графической сессии права
запрашиваются через polkit, в терминале нужен `sudo redos`. **Только Linux.**

## `/passwd-policy` — детали

Полноэкранный режим с тремя действиями:

- **Применить пресет «Базовая»** — `minlen=8`, `minclass=3`, `PASS_MAX_DAYS=90`. Опционально применяет `chage -M -m -W` к выбранным пользователям.
- **Применить пресет «Усиленная»** — `minlen=10`, `minclass=4`, `PASS_MAX_DAYS=60`. То же самое для существующих пользователей.
- **Форсировать смену пароля при входе** — `chage -d 0` для выбранных пользователей; при ближайшем входе система потребует новый пароль.

Куда пишутся настройки:

| Файл | Что |
|---|---|
| `/etc/security/pwquality.conf.d/50-redos.conf` | Параметры сложности (drop-in, основной `pwquality.conf` не трогается) |
| `/etc/login.defs` | `PASS_MAX_DAYS`, `PASS_MIN_DAYS`, `PASS_WARN_AGE`. Перед записью создаётся `*.bak.YYYYMMDD-HHMMSS` |
| `/etc/shadow` (через `chage`) | Сроки и флаг «сменить при входе» для существующих пользователей |

PAM-стек `/etc/pam.d/system-auth` / `password-auth` **не редактируется** — он управляется `authselect`. `pam_pwquality` уже подключён в нём по умолчанию и подхватывает drop-in.

## `/usb-policy` — контроль устройств

Блокировка работает **на уровне ядра**: устройству вне политики снимается
авторизация (`0` в `/sys/…/authorized`), ядро отвязывает драйверы, узла
`/dev/sdX` не появляется — смонтировать нечего даже root. Всё делается штатным
udev, без пакетов из репозитория: на изолированной машине это важно.

> Механизм на udev-подсказке `UDISKS_IGNORE` (redos ≤ 0.9) не блокировал: он
> гасил только автомонтирование. Устройство оставалось авторизованным, а polkit
> по умолчанию разрешает активному локальному пользователю монтировать без
> пароля — через «Диски» или `udisksctl mount`.
>
> Версии 0.10–0.11 использовали [USBGuard](https://usbguard.github.io). Он
> решает раньше — до конфигурации устройства, — но требует пакета из
> репозитория. Если контроль на нём уже включён, экран это увидит и предложит
> убрать: остановить службу, вернуть `authorized_default` на контроллерах (иначе
> новые устройства не поднимутся до перезагрузки), разблокировать устройства и
> удалить пакет.

### Модель

Администратор **блокирует группу** устройств и **разрешает отдельные**.

| | |
|---|---|
| Блокируются категориями | накопители, веб-камеры, звук, сеть и модемы, Bluetooth |
| Разрешены всегда | хабы, клавиатуры и мыши, принтеры, сканеры, смарт-карты, криптотокены |
| Разрешаются поимённо | любое устройство из списка исключений |

Политика — белый список: разрешено только явно разрешённое. Обратная модель
(«разрешено всё, блокируем выбранное») ненадёжна — встроенный картридер Realtek
объявляет класс `ff:06:50`, а не `08`, и из чёрного списка по классу накопителей
просто выпал бы.

Категории — это классы интерфейсов USB по спецификации usb.org, те же самые, что
USBGuard принимает в `with-interface`. udev видит их напрямую: как
`ATTR{bInterfaceClass}` на событии и как файлы `bInterfaceClass` в sysfs.

### Что появляется на машине

| файл | зачем |
|---|---|
| `/etc/udev/rules.d/99-block-usb.rules` | два правила: вызвать скрипт на событии `usb_interface` и на появлении блочного узла |
| `/usr/local/sbin/redos-block-usb.sh` | решение по устройству целиком |
| `/etc/redos/device-control.conf` | сама политика — её читают и скрипт, и утилита |

Политика вынесена из правил в отдельный файл намеренно: решение принимается по
**всем** интерфейсам устройства сразу, а udev-правило видит их по одному.

```
ALLOWED_CLASSES=03 06 07 08 09 0b     # разрешённые классы интерфейсов
TOKEN_IDS=0a89:0001 0a89:0004 …       # криптотокены — поимённо, не 0a89:*
TRUSTED=0951:16aa:60A44C4…            # исключения: vendor:product:serial
```

Заблокированных устройств в файле нет вообще — блокирует отсутствие разрешения.
`match-all` вместо `one-of` принципиален: устройство проходит, только если **все**
его интерфейсы в разрешённом наборе, иначе комбо «флешка + клавиатура» прошло бы
по одному лишь HID.

### Снятие блокировки действует сразу

Разрешили категорию или внесли устройство в исключения — флешка возвращается
без похода к машине: узел `/dev/sdX` появляется, монтирование работает как
обычно.

Само по себе это не следует из правил. Деавторизованное устройство остаётся
в дереве `/sys`, но интерфейсов у него нет — ядро их не конфигурирует, — а
правило висит на событии `usb_interface`. Событий по такому устройству не
порождает даже `udevadm trigger`, поэтому `authorized=0` переживает и новую
политику, и перечитывание правил: до 0.12.0 разблокированная флешка не
появлялась, пока её физически не вытащишь и не вставишь.

Поэтому применение политики сначала возвращает авторизацию всем заблокированным
устройствам и ждёт, пока ядро поднимет интерфейсы, и только потом прогоняет
правила. Устройство проходит тот же путь, что при физическом переподключении;
то, что политика по-прежнему запрещает, гасится здесь же — на событии
интерфейса, до появления блочного узла.

### Что показывает экран

Колонка **статус** — состояние устройства в ядре прямо сейчас: «разрешено» или
«заблокировано». Если невыполненный выбор его меняет, статус показывается со
стрелкой — «→ разрешить», «→ блокировать»: решение принято, но политика ещё
не применена.

Колонка **тип** и строка под таблицей объясняют решение по выделенному
устройству: какой класс интерфейса не прошёл и включается ли он галочкой
вообще. У заблокированного устройства ядро интерфейсы не конфигурирует, и
классы берутся из его дескрипторов — сам файл `descriptors` в sysfs остаётся
на месте. Такие данные помечаются «со слов устройства»: решение по ним не
принимается, политику применяет скрипт по тому, что ядро действительно
сконфигурировало.

### Устройства вне категорий

Класс интерфейса описывает не всё. Встроенный картридер Realtek объявляет
`ff:06:50`, Wi-Fi-донгл RTL8188 — `ff:ff:ff`: вендорский класс, по которому
категорию не определить. Разбираются они по-разному.

**Картридер — накопитель, и политика это видит.** Подкласс `06` — SCSI,
протокол `50` — Bulk-Only Transport; ядро опознаёт его так же, привязывая
`ums-realtek` по совпадению класса, подкласса и протокола. Поэтому интерфейс с
SCSI-переносом считается накопителем, каким бы класс себя ни называл, и
подчиняется галочке «Накопители» — в обе стороны. Замаскированный накопитель
этой же нормализацией попадает **под** запрет категории, а не выходит из-под
него.

**Донглу помочь нечем.** У `ff:ff:ff` вендорское всё, назначение из
дескриптора не следует. Категория «сеть и модемы» его не разрешает: она про
классы `02`, `0a` и `e0`, а он ни одного не объявляет. Разрешить такое
устройство можно только поимённо, в исключениях, — и это не обходной путь, а
рекомендованный: udev-белый список
([Gentoo Wiki](https://wiki.gentoo.org/wiki/Allow_only_known_usb_devices))
строится на `idVendor`/`idProduct`/`serial` именно потому, что классу нельзя
доверять.

### Второй рубеж: блочный узел

Политика по классам верит дескриптору, а ядро привязывает драйверы **ещё и по
`vid:pid`**. Устройство, объявившее себя клавиатурой, но подставившее
идентификаторы известного накопителя, получит `usb-storage`: класс остаётся
разрешённым, и рубеж по интерфейсам такое пропускает. Обход описан в
[разборе Pulse Security](https://pulsesecurity.co.nz/advisories/usbguard-bypass)
и применим к любой политике по классам интерфейсов, не только к USBGuard.

Поэтому правил два. Второе срабатывает на появлении блочного узла: если у
USB-устройства возник диск, а накопители не разрешены и само оно не в
исключениях, авторизация снимается. Класс здесь не спрашивается вовсе — он и
был тем, чему верить нельзя. Появившийся `/dev/sdX` подделать уже нечем: это
факт, а не заявление устройства о себе.

> Версия формата политики — 3. Если на машине лежит файл прошлой версии, экран
> скажет об этом: скрипт и правило обновляются только повторным применением.

### Криптотокены

Разрешены всегда и опознаются по производителю, а не по классу: `Rutoken lite HID`
и `Rutoken ECP HID` объявляют себя устройствами ввода, `Rutoken Mass Storage` —
накопителем, `Rutoken S` — вендорским классом. Запрет накопителей иначе отрубил бы
вход по токену и подпись.

## `/printer` — печать и сканирование

Две задачи из практики с HP LaserJet MFP M426fdn на РедОС 8.

### «Принтер отвалился»

При разовой ошибке бэкенда CUPS по умолчанию (`error-policy=stop-printer`)
останавливает очередь и **сам её обратно не включает** — печать пропадает до
ручного вмешательства. Особенно часто это даёт бэкенд hplip (`hp:/net/...`,
`open device failed stat=12`), когда МФУ уснул или занят. В журнале видно
`Printer stopped due to backend errors`.

**Диагностика очереди** показывает состояние, `error-policy`, ping до аппарата,
порты 631/9100, ответ по eSCL и последние записи об ошибках из журнала cups.

**Починить очередь** делает то, что лечит проблему насовсем:

| Шаг | Зачем |
|---|---|
| `lpadmin -v ipp://IP/ipp/print -m everywhere` | уход с ненадёжного hplip на драйверless IPP Everywhere |
| `lpadmin -o printer-error-policy=retry-job` | CUPS больше не останавливает очередь из-за разовой ошибки |
| `cupsenable` + `cupsaccept` | включить очередь и приём заданий |
| `cancel -a` | снять застрявшие задания, они мешают следующим |

### «Только один МФУ»

Если в сети несколько одинаковых аппаратов, через mDNS они все лезут в списки
печати и сканирования — на каждый ещё и по два сканера (airscan и hpaio).
Пользователь выбирает не тот и «принтер не печатает».

Мастер ищет аппараты по mDNS и через CUPS, опрашивает их по eSCL (кто ответил —
настоящий МФУ со сканером), либо принимает IP вручную. После подтверждения:

| Что делается | Результат |
|---|---|
| очередь на `ipp://IP/ipp/print` + `retry-job` | одна рабочая очередь |
| остальные очереди удаляются | в списке печати ровно один принтер |
| `/etc/sane.d/dll.conf` → только `airscan` | лишние бэкенды сканирования отключены |
| `/etc/sane.d/dll.d/hpaio` → `.disabled` | hpaio дублировал тот же аппарат |
| `/etc/sane.d/airscan.conf` → `discovery = disable` + устройство по IP | автопоиск не подтягивает чужие сканеры |
| `systemctl mask avahi-daemon` (можно отключить клавишей `A`) | mDNS больше не показывает чужие аппараты |

Перед изменениями создаётся бэкап `/root/redos-mfp-backup-<дата>/` со скриптом
`rollback.sh`. Удалённые очереди печати он не восстанавливает — их заводят заново.

> Экран подтверждения перечисляет все необратимые изменения до их применения.
