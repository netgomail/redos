# РедОС

> Консольная утилита для специалиста по защите информации — парольная и USB-политики, печать и сканирование, инвентаризация Linux-систем. Заточена под РедОС 7/8 (RHEL-based).

---

## Установка

```bash
curl -fsSL https://raw.githubusercontent.com/netgomail/redos/master/install.sh | bash
```

Установщик автоматически скачивает последнюю версию из GitHub Releases и добавляет `redos` в PATH.

---

## Запуск

```bash
redos
```

Команды вроде `/passwd-policy` и `/usb-policy` требуют root — в графической
сессии права запросятся сами (polkit), в терминале нужно `sudo redos`.

---

## Обновление

Происходит само при запуске: `redos` в фоне проверяет GitHub Releases и,
если есть новая версия, сразу её ставит. После этого в шапке появится
напоминание перезапустить приложение.

Если нужно обновиться вручную (например, автопроверке не хватило доступа
к сети при старте):

```bash
redos update
```

## `/passwd-policy` — детали

Полноэкранный режим с тремя действиями:

- **Применить пресет «Базовая»** — `minlen=8`, `minclass=3`, `PASS_MAX_DAYS=90`. Опционально применяет `chage -M -m -W` к выбранным пользователям.
- **Применить пресет «Усиленная»** — `minlen=10`, `minclass=4`, `PASS_MAX_DAYS=60`. То же самое для существующих пользователей.
- **Форсировать смену пароля при входе** — `chage -d 0` для выбранных пользователей; при ближайшем входе система потребует новый пароль.

Куда пишутся настройки:

| Файл | Что |
|---|---|
| `/etc/security/pwquality.conf.d/50-redos.conf` | Параметры сложности (drop-in, основной `pwquality.conf` не трогается) |
| `/etc/login.defs` | `PASS_MAX_DAYS`, `PASS_MIN_DAYS`, `PASS_WARN_AGE`. Перед записью создаётся `*.bak.YYYYMMDD-HHMMSS` |
| `/etc/shadow` (через `chage`) | Сроки и флаг «сменить при входе» для существующих пользователей |

PAM-стек `/etc/pam.d/system-auth` / `password-auth` **не редактируется** — он управляется `authselect`. `pam_pwquality` уже подключён в нём по умолчанию и подхватывает drop-in.

## `/usb-policy` — контроль устройств

Блокировка работает **на уровне ядра**: устройству вне политики снимается
авторизация (`0` в `/sys/…/authorized`), ядро отвязывает драйверы, узла
`/dev/sdX` не появляется — смонтировать нечего даже root. Всё делается штатным
udev, без пакетов из репозитория: на изолированной машине это важно.

> Механизм на udev-подсказке `UDISKS_IGNORE` (redos ≤ 0.9) не блокировал: он
> гасил только автомонтирование. Устройство оставалось авторизованным, а polkit
> по умолчанию разрешает активному локальному пользователю монтировать без
> пароля — через «Диски» или `udisksctl mount`.
>
> Версии 0.10–0.11 использовали [USBGuard](https://usbguard.github.io). Он
> решает раньше — до конфигурации устройства, — но требует пакета из
> репозитория. Если контроль на нём уже включён, экран это увидит и предложит
> убрать: остановить службу, вернуть `authorized_default` на контроллерах (иначе
> новые устройства не поднимутся до перезагрузки), разблокировать устройства и
> удалить пакет.

### Модель

Администратор **блокирует группу** устройств и **разрешает отдельные**.

| | |
|---|---|
| Блокируются категориями | накопители, веб-камеры, звук, сеть и модемы, Bluetooth |
| Разрешены всегда | хабы, клавиатуры и мыши, принтеры, сканеры, смарт-карты, криптотокены |
| Разрешаются поимённо | любое устройство из списка исключений |

Политика — белый список: разрешено только явно разрешённое. Обратная модель
(«разрешено всё, блокируем выбранное») ненадёжна — встроенный картридер Realtek
объявляет класс `ff:06:50`, а не `08`, и из чёрного списка по классу накопителей
просто выпал бы.

Категории — это классы интерфейсов USB по спецификации usb.org, те же самые, что
USBGuard принимает в `with-interface`. udev видит их напрямую: как
`ATTR{bInterfaceClass}` на событии и как файлы `bInterfaceClass` в sysfs.

### Что появляется на машине

| файл | зачем |
|---|---|
| `/etc/udev/rules.d/99-block-usb.rules` | два правила: вызвать скрипт на событии `usb_interface` и на появлении блочного узла |
| `/usr/local/sbin/redos-block-usb.sh` | решение по устройству целиком |
| `/etc/redos/device-control.conf` | сама политика — её читают и скрипт, и утилита |

Политика вынесена из правил в отдельный файл намеренно: решение принимается по
**всем** интерфейсам устройства сразу, а udev-правило видит их по одному.

```
ALLOWED_CLASSES=03 06 07 08 09 0b     # разрешённые классы интерфейсов
TOKEN_IDS=0a89:0001 0a89:0004 …       # криптотокены — поимённо, не 0a89:*
TRUSTED=0951:16aa:60A44C4…            # исключения: vendor:product:serial
```

Заблокированных устройств в файле нет вообще — блокирует отсутствие разрешения.
Проверяются **все** интерфейсы устройства, а не один: иначе комбо «флешка +
клавиатура» прошло бы по одному лишь HID.

Блокирует интерфейс, чей класс относится к **выключенной** категории. Класс,
не покрытый категориями вовсе, устройство не блокирует — включить его всё
равно нечем, галочки для него не существует. Пройти по одному такому классу
тоже нельзя: нужен хотя бы один интерфейс из разрешённых.

Разница не теоретическая. Принтеры HP объявляют, кроме `07`, ещё и
проприетарный `ff` — и пока проверка требовала разрешения для каждого
интерфейса, **ни один аппарат HP не работал** даже при всех включённых
категориях, хотя «Принтеры» стоят в locked как рабочая необходимость. Если у
МФУ есть ещё и слот карт (`08`), он по-прежнему подчиняется галочке
«Накопители» — это запрет по существу, а не из-за непонятного класса.

### Снятие блокировки действует сразу

Разрешили категорию или внесли устройство в исключения — флешка возвращается
без похода к машине: узел `/dev/sdX` появляется, монтирование работает как
обычно.

Само по себе это не следует из правил. Деавторизованное устройство остаётся
в дереве `/sys`, но интерфейсов у него нет — ядро их не конфигурирует, — а
правило висит на событии `usb_interface`. Событий по такому устройству не
порождает даже `udevadm trigger`, поэтому `authorized=0` переживает и новую
политику, и перечитывание правил: до 0.12.0 разблокированная флешка не
появлялась, пока её физически не вытащишь и не вставишь.

Поэтому применение политики сначала возвращает авторизацию всем заблокированным
устройствам и ждёт, пока ядро поднимет интерфейсы, и только потом прогоняет
правила. Устройство проходит тот же путь, что при физическом переподключении;
то, что политика по-прежнему запрещает, гасится здесь же — на событии
интерфейса, до появления блочного узла.

### Что показывает экран

Колонка **статус** — состояние устройства в ядре прямо сейчас: «разрешено» или
«заблокировано». Если невыполненный выбор его меняет, статус показывается со
стрелкой — «→ разрешить», «→ блокировать»: решение принято, но политика ещё
не применена.

Колонка **тип** и строка под таблицей объясняют решение по выделенному
устройству: какой класс интерфейса не прошёл и включается ли он галочкой
вообще. У заблокированного устройства ядро интерфейсы не конфигурирует, и
классы берутся из его дескрипторов — сам файл `descriptors` в sysfs остаётся
на месте. Такие данные помечаются «со слов устройства»: решение по ним не
принимается, политику применяет скрипт по тому, что ядро действительно
сконфигурировало.

### Устройства вне категорий

Класс интерфейса описывает не всё. Встроенный картридер Realtek объявляет
`ff:06:50`, Wi-Fi-донгл RTL8188 — `ff:ff:ff`: вендорский класс, по которому
категорию не определить. Разбираются они по-разному.

**Картридер — накопитель, и политика это видит.** Подкласс `06` — SCSI,
протокол `50` — Bulk-Only Transport; ядро опознаёт его так же, привязывая
`ums-realtek` по совпадению класса, подкласса и протокола. Поэтому интерфейс с
SCSI-переносом считается накопителем, каким бы класс себя ни называл, и
подчиняется галочке «Накопители» — в обе стороны. Замаскированный накопитель
этой же нормализацией попадает **под** запрет категории, а не выходит из-под
него.

**Донглу помочь нечем.** У `ff:ff:ff` вендорское всё, назначение из
дескриптора не следует. Категория «сеть и модемы» его не разрешает: она про
классы `02`, `0a` и `e0`, а он ни одного не объявляет. Других интерфейсов у
донгла нет, поэтому разрешать ему нечего — в отличие от принтера, где рядом
с вендорским `ff` есть настоящий `07`. Разрешить такое
устройство можно только поимённо, в исключениях, — и это не обходной путь, а
рекомендованный: udev-белый список
([Gentoo Wiki](https://wiki.gentoo.org/wiki/Allow_only_known_usb_devices))
строится на `idVendor`/`idProduct`/`serial` именно потому, что классу нельзя
доверять.

### Второй рубеж: блочный узел

Политика по классам верит дескриптору, а ядро привязывает драйверы **ещё и по
`vid:pid`**. Устройство, объявившее себя клавиатурой, но подставившее
идентификаторы известного накопителя, получит `usb-storage`: класс остаётся
разрешённым, и рубеж по интерфейсам такое пропускает. Обход описан в
[разборе Pulse Security](https://pulsesecurity.co.nz/advisories/usbguard-bypass)
и применим к любой политике по классам интерфейсов, не только к USBGuard.

Поэтому правил два. Второе срабатывает на появлении блочного узла: если у
USB-устройства возник диск, а накопители не разрешены и само оно не в
исключениях, авторизация снимается. Класс здесь не спрашивается вовсе — он и
был тем, чему верить нельзя. Появившийся `/dev/sdX` подделать уже нечем: это
факт, а не заявление устройства о себе.

> Версия формата политики — 4. Если на машине лежит файл прошлой версии, экран
> скажет об этом: скрипт и правило обновляются только повторным применением.

### Криптотокены

Разрешены всегда и опознаются по производителю, а не по классу: `Rutoken lite HID`
и `Rutoken ECP HID` объявляют себя устройствами ввода, `Rutoken Mass Storage` —
накопителем, `Rutoken S` — вендорским классом. Запрет накопителей иначе отрубил бы
вход по токену и подпись.

## `/printer` — печать и сканирование

Перевод МФУ HP (из практики — LaserJet Pro MFP M426fdn на РедОС 8) с hplip на
driverless: печать по IPP Everywhere, сканирование по eSCL. Аппарат может быть
подключён **по сети или по USB** — см. «Аппарат на USB».

### Почему не hplip

Очередь на бэкенде hplip (`hp:/net/...`) перед каждым заданием читает device-id
аппарата по SNMP. Если МФУ спит или пакет потерялся, в журнале cups появляется
`unable to read device-id` / `open device failed stat=12`, бэкенд падает, и CUPS
по умолчанию (`error-policy=stop-printer`) **останавливает очередь насовсем**.
Пока у пользователей был sudo, её незаметно включали через HP Device Manager;
без sudo печать пропадает до прихода администратора.

Драйвер `everywhere` строит PPD по ответу самого аппарата и печатает по IPP на
порт 631 — без hplip и SNMP. С `retry-job` разовая ошибка очередь не
останавливает.

### Главный экран

Очереди (бэкенд, IP, остановлена ли), состояние системы (установлен ли hplip,
работает ли hp-systray, выключено ли автообнаружение, настроен ли сканер) и
действия:

| Действие | Что делает |
|---|---|
| **Диагностика очереди** | очередь и `error-policy`; МФУ по IPP — состояние, ошибки (замятие, открыта дверца), тонер, поддержка IPP Everywhere; ping, порт 631, eSCL; сбои hplip в журнале cups. Итог — рекомендация: перевести, включить очередь или проблема в самом МФУ |
| **Перевести на driverless...** | мастер, см. ниже |
| **Включить остановленную очередь** | `retry-job`, `cupsenable`, `cupsaccept`, снятие застрявших заданий — бэкенд не меняется |

Состояние МФУ читается встроенным IPP-клиентом (`src/features/ipp.ts`,
Get-Printer-Attributes) по http на порт 631 — `cups-ipptool` не нужен. HTTPS
к веб-интерфейсу МФУ перехватывает Kaspersky Endpoint Security (самоподписанный
сертификат), IPP на 631 он не трогает.

### Мастер перевода

1. Выбор аппарата: принтеры на USB (из sysfs — они подключены прямо сейчас),
   затем сетевые адреса из очередей и `airscan.conf`, найденные CUPS и mDNS
   (если avahi ещё работает), либо ввод IP вручную.
2. Проверка МФУ. Сеть: ping, порт 631, IPP, наличие PWG-raster/URF — без них
   перевод заблокирован. USB: умеет ли аппарат IPP-over-USB и не заблокирован
   ли он политикой `/usb-policy`.
3. Экран параметров показывает **точный список шагов** до применения;
   уже сделанное (замаскированные службы, настроенный сканер) в план не попадает.
   Первая строка — **имя очереди**: подставляется прежнее (под ним печатают и
   его видят в списке принтеров), но его можно изменить — Enter, ввод, Enter.
   Запрещённое CUPS (пробел, `/`, `#`, пусто, длиннее 127) отсекается сразу, а
   не после начала работы. `D` — применить.

| Шаг | Детали |
|---|---|
| бэкап | `/root/redos-printer-backup-<дата>/etc.tgz` (`/etc/cups`, `/etc/sane.d`, lpoptions пользователей) + `rollback.sh` |
| ipp-usb (только USB) | `dnf install -y ipp-usb`, `systemctl enable --now ipp-usb`; делается **до** очереди и любых удалений — не поднялся, ничего не тронуто |
| очередь | `lpadmin -p <имя> -v ipp://IP/ipp/print -m everywhere -o printer-error-policy=retry-job -o sides-default=one-sided -o Duplex=None`, включить, по умолчанию. Имя сохраняется — берётся существующая очередь на этот IP |
| лишние очереди | удаляются очереди **того же аппарата** (по выбору — вообще все остальные); их строки убираются из `lpoptions` пользователей |
| автообнаружение | `cups-browsed`, `avahi-daemon` — stop + mask, `cupsctl --no-share-printers --no-remote-any`; только то, что ещё не выключено. После `cupsctl` ждём, пока cupsd снова примет запросы |
| сканер | `sane-airscan` (ставится при отсутствии), `airscan.conf`: устройство `http://IP/eSCL/` (у USB — `http://127.0.0.1:<порт>/eSCL/`), `discovery = disable` |
| тестовая страница | `lp` через новую очередь, ждём завершения до 2 минут, проверяем, что очередь не остановилась |
| hplip | `dnf remove` пакетов hplip и `libsane-hpaio`, остановка hp-systray. **Только если тестовая страница прошла и на hplip не осталось живых очередей** |

После перевода: перезагрузка и печать из LibreOffice и браузера под обычным
пользователем.

### Аппарат на USB

У МФУ на USB порта 631 нет, и hplip был единственным способом с ним говорить.
Driverless по USB даёт демон **ipp-usb**: он публикует устройство на
`127.0.0.1:60000`, и дальше всё то же самое — `lpadmin -m everywhere` по этому
адресу, `retry-job`, eSCL на том же порту для сканирования. Ни hplip, ни PPD
не нужны.

Условие одно: аппарат должен уметь **IPP-over-USB**. Признак читается из
sysfs — интерфейс класса `07` с протоколом `04`. Проверить руками:

```
for i in /sys/bus/usb/devices/*/; do
  [ -r "$i/idVendor" ] || continue
  printf '%s %s:%s %s\n' "${i##*/}" "$(cat $i/idVendor)" "$(cat $i/idProduct)" "$(cat $i/product 2>/dev/null)"
  for f in $i*:*/bInterfaceClass; do d=${f%/bInterfaceClass}
    printf '    %s:%s:%s\n' "$(cat $f)" "$(cat $d/bInterfaceSubClass)" "$(cat $d/bInterfaceProtocol)"
  done
done
```

Не умеет — мастер говорит это прямо и очередь не трогает: hplip остаётся, а
не удаляется в никуда.

Отсутствие самого `ipp-usb` переводу не мешает — это шаг плана, а не отказ:
демон ставится и запускается до создания очереди, и аппарат опрашивается уже
после. Маскировка `avahi` на печать по USB не влияет: очередь задана адресом
и от mDNS не зависит.

> Аппарат на USB может быть заблокирован политикой `/usb-policy` — мастер
> покажет это и отправит разрешить его там.

### Почему hplip не удаляется сам собой

Удаление hplip — следствие, а не отдельное желание: пакет уходит, когда на нём
не осталось ни одной живой очереди. Если переводится сетевой МФУ, а рядом
работает USB-принтер на `hp:/usb/...`, hplip остаётся, и экран говорит, какие
очереди его держат. Переведите их тем же мастером — удаление появится в плане
само.

Раньше было иначе, и это ломало машины: любая очередь на hplip считалась
мусором и удалялась заодно с сетевой, а следом сносился и сам пакет — рабочий
USB-принтер после перевода соседнего сетевого МФУ переставал печатать вовсе.

### Сломанный принтер и очередь из копий

Когда аппарат неисправен, пользователь жмёт «печать» снова и снова, и в
очереди оказывается один и тот же документ по десять раз. Диагностика это
показывает отдельно — имена документов берутся из `lpq`, повторы считаются, —
и предлагает **закрыть очередь**: снять всё и перестать принимать задания
(`cupsreject`). Тогда человек получает отказ сразу и видит, что печать не
работает, а не копит копии в надежде. Обратно открывает «Включить
остановленную очередь».

На самих МФУ (вручную, через веб-интерфейс по http): выключить Bonjour,
WS-Discovery, SLP, LLMNR; IPP и eSCL оставить; задать пароль администратора.

---|---|
| `lpadmin -v ipp://IP/ipp/print -m everywhere` | уход с ненадёжного hplip на драйверless IPP Everywhere |
| `cancel -a` (отдельным действием) | снять из очереди всё |
| `cupsreject` + `cancel -a` | «принтер в ремонте»: отказ вместо накопления копий |
| `lpadmin -o printer-error-policy=retry-job` | CUPS больше не останавливает очередь из-за разовой ошибки |
| `cupsenable` + `cupsaccept` | включить очередь и приём заданий |
| `cancel -a` | снять застрявшие задания, они мешают следующим |

### «Только один МФУ»

Если в сети несколько одинаковых аппаратов, через mDNS они все лезут в списки
печати и сканирования — на каждый ещё и по два сканера (airscan и hpaio).
Пользователь выбирает не тот и «принтер не печатает».

Мастер ищет аппараты по mDNS и через CUPS, опрашивает их по eSCL (кто ответил —
настоящий МФУ со сканером), либо принимает IP вручную. После подтверждения:

| Что делается | Результат |
|---|---|
| очередь на `ipp://IP/ipp/print` + `retry-job` | одна рабочая очередь |
| остальные очереди удаляются | в списке печати ровно один принтер |
| `/etc/sane.d/dll.conf` → только `airscan` | лишние бэкенды сканирования отключены |
| `/etc/sane.d/dll.d/hpaio` → `.disabled` | hpaio дублировал тот же аппарат |
| `/etc/sane.d/airscan.conf` → `discovery = disable` + устройство по IP | автопоиск не подтягивает чужие сканеры |
| `systemctl mask avahi-daemon` (можно отключить клавишей `A`) | mDNS больше не показывает чужие аппараты |

Перед изменениями создаётся бэкап `/root/redos-mfp-backup-<дата>/` со скриптом
`rollback.sh`. Удалённые очереди печати он не восстанавливает — их заводят заново.

> Экран подтверждения перечисляет все необратимые изменения до их применения.

## `/install` — установка сторонних программ

Реестр программ, не входящих в РедОС из коробки — ставятся в домашний каталог
оператора, поэтому root не требуется (в отличие от остальных команд). Список
программ — массив `INSTALL_APPS` в `src/features/install.ts`; добавить новую
программу — значит добавить туда один объект.

Первая запись — **«АС Смета»** (клиент ЭДО «Смета», Krista): скачивает
`stimrun` по прямой ссылке, кладёт в `~/stimate/`, выставляет права `755`
(чтение и выполнение — всем, запись — только владельцу), создаёт ярлык на
рабочем столе и в меню приложений и прописывает сервер авторизации
`10.31.22.10:8080` в `~/stimate/stimate.ini` — вводить вручную не нужно. Если
`~/.config/stimate/reg.xml` ещё не существует, создаётся и он с тем же
адресом (`AppServer`); существующий файл не трогается — там может быть
накопленное состояние программы.

Ссылка на скачивание — публичная ссылка Nextcloud/ownCloud: сервер отвечает
редиректом с cookie сессии, без переноса cookie на следующий запрос отдаёт
ошибку — поэтому редиректы обрабатываются вручную (`fetchFollowingRedirects`
в `src/features/install.ts`), а не через встроенный редирект `fetch()`.
